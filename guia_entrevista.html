Material de estudio

¿Qué es FastAPI?

▼

FastAPI es un framework web Python moderno y de alto rendimiento para construir APIs. Sus ventajas principales:

  • Tipado nativo: usa type hints de Python para validar datos automáticamente con Pydantic.
  • Documentación automática: genera Swagger UI en /docs y ReDoc en /redoc sin configuración extra.
  • Async nativo: soporta async/await para operaciones concurrentes.
  • Inyección de dependencias: sistema de Depends() para compartir lógica entre endpoints.
# Ejemplo mínimo
from fastapi import FastAPI
app = FastAPI()

@app.get("/items/{item_id}")
def read_item(item_id: int):  # FastAPI valida que item_id sea int
    return {"id": item_id}
En tu proyecto, los routers (users, items, auth) se registran con app.include_router() para separar el código por dominio.

JWT — JSON Web Tokens

▼

Un JWT es un token firmado que el servidor emite al autenticar a un usuario. Tiene tres partes separadas por puntos:

eyJhbGciOiJIUzI1NiJ9  .  eyJzdWIiOiJhZG1pbiJ9  .  firma
      HEADER                    PAYLOAD                 SIGNATURE
  • Header: algoritmo de firma (en tu proyecto: HS256)
  • Payload: datos del token. En tu proyecto: sub (username), role, exp (expiración)
  • Signature: HMAC del header+payload firmado con la SECRET_KEY. Garantiza que no fue modificado.

El payload no está encriptado, solo firmado. No guardes datos sensibles ahí.

Flujo completo en tu proyecto:

1
Cliente hace POST /login con username y password
2
authenticate_user busca el usuario en la DB y llama a verify_password
3
create_access_token genera un JWT firmado con SECRET_KEY, expira en 30 min
4
Cliente guarda el token en localStorage y lo manda en cada request: Authorization: Bearer <token>
5
get_current_user decodifica el JWT, extrae el sub (username), busca el usuario en la DB y lo devuelve
JWT es stateless — el servidor no guarda los tokens. No se pueden invalidar sin una blacklist o cambiar la SECRET_KEY.

Depends() — Inyección de dependencias

▼

FastAPI resuelve automáticamente las dependencias declaradas con Depends() antes de ejecutar el endpoint. Se pueden encadenar:

# get_current_user verifica el JWT
def get_current_user(token = Depends(oauth2_scheme), session = Depends(get_session)):
    payload = jwt.decode(token, SECRET_KEY, ...)
    user = session.exec(select(User).where(...)).first()
    return user

# require_admin usa get_current_user como dependencia
def require_admin(current_user = Depends(get_current_user)):
    if current_user.role != UserRole.ADMIN:
        raise HTTPException(403)
    return current_user

# El endpoint solo declara require_admin, FastAPI resuelve la cadena
@router.delete("/{user_id}")
def delete_user(current_user = Depends(require_admin)):
    ...
Ventaja: si la lógica de autenticación cambia, la cambiás en un solo lugar y afecta a todos los endpoints que la usan.

SQLModel — Modelos y Schemas

▼

SQLModel une SQLAlchemy (ORM para DB) con Pydantic (validación). Los modelos con table=True son tablas en la DB; los sin table=True son schemas de validación.

# models.py — tabla real en la DB
class User(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    username: str = Field(index=True)  # índice para búsquedas rápidas
    hashed_password: str               # nunca la password en texto plano
    role: UserRole = Field(default=UserRole.USER)

# schemas.py — lo que entra y sale por la API
class UserCreate(UserBase):
    password: str  # recibe la password en texto plano

class UserRead(UserBase):
    id: int
    # ↑ NO incluye hashed_password — no se expone nunca

El ciclo al crear un usuario:

1
FastAPI valida el request body contra UserCreate
2
create_user hashea la password y crea un objeto User (modelo de DB)
3
session.add() + session.commit() persisten el objeto en SQLite
4
FastAPI serializa la respuesta con UserRead — sin la password

Alembic — Migraciones de base de datos

▼

Una migración es un script que describe cómo evoluciona el esquema de la DB. En tu proyecto, Alembic corre automáticamente al levantar Docker.

  • create_all: crea tablas que no existen, pero si la tabla ya tiene datos y cambiás el modelo, no hace nada.
  • Alembic: genera scripts incrementales que podés aplicar (upgrade) y revertir (downgrade). Ideal para producción donde no podés borrar la DB.
# Comandos que usaste
alembic upgrade head     # aplica todas las migraciones pendientes
alembic downgrade -1     # revierte la última migración
Tu env.py usa SQLModel.metadata como target_metadata. Esto permite a Alembic detectar los modelos automáticamente para generar migraciones con alembic revision --autogenerate.

Testing con pytest y FastAPI

▼

Tus tests usan tres piezas clave:

# 1. DB en memoria — no toca database.db
engine = create_engine("sqlite://", poolclass=StaticPool,
    connect_args={"check_same_thread": False})

# 2. Fixture con yield — crea la DB, la usa, la destruye
@pytest.fixture
def session_fixture():
    SQLModel.metadata.create_all(engine)   # setup
    with Session(engine) as session:
        yield session                       # ← acá corre el test
    SQLModel.metadata.drop_all(engine)     # teardown

# 3. Override de dependencias — reemplaza la DB real con la de tests
def override_get_session():
    return session

app.dependency_overrides[get_session] = override_get_session

Tipos de tests que escribiste:

  • Happy path: test_create_user, test_create_item — flujo normal, espera 200
  • Validaciones: test_create_user_username_duplicado — espera 409
  • Permisos: test_user_sin_rol_admin_no_puede_borrar — espera 403
  • Not found: test_get_user_inexistente — espera 404
  • Lógica de negocio: test_item_repetido_suma_cantidad — verifica la acumulación
StaticPool fuerza a SQLAlchemy a reutilizar la misma conexión en memoria entre el fixture y el test. Sin esto, cada conexión nueva vería una DB vacía.

Lógica de negocio — Roles y permisos

▼

Tu sistema tiene dos roles definidos con un StrEnum:

class UserRole(StrEnum):
    ADMIN = "admin"
    USER  = "user"

Qué puede hacer cada rol:

  • USER: ver usuarios, crear items propios, eliminar sus propios items, ver sus propios items
  • ADMIN: todo lo anterior + eliminar cualquier usuario (excepto a sí mismo)

La lógica de acumulación de items en POST /items/: si ya tenés un "Mouse" con cantidad 2 y creás otro "Mouse" con cantidad 3, el resultado es un solo "Mouse" con cantidad 5. Esto es lógica de negocio propia — no viene de ningún tutorial.

Función 2: decode del JWT en el frontend

Esta es la línea más interesante del JS — decodifica el payload del token sin hacer ningún request al servidor:

const payload = JSON.parse(atob(token.split('.')[1]));todo en una línea — se lee de adentro hacia afuera

Desglosado paso a paso con un token real:

1
token.split('.') — divide el JWT por el punto
["eyJhbGciOiJIUzI1NiJ9", "eyJzdWIiOiJhZG1pbiIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTc0OX0", "firma"]
2
[1] — toma solo el segundo elemento (el payload)
"eyJzdWIiOiJhZG1pbiIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTc0OX0"
3
atob(...) — decodifica Base64 a string legible
'{"sub":"admin","role":"admin","exp":1749...}'
4
JSON.parse(...) — convierte el string JSON en objeto JavaScript
{ sub: "admin", role: "admin", exp: 1749... }
Esto funciona porque el payload de un JWT es solo Base64, no está encriptado. Por eso el frontend puede leer el username y el rol sin hacer un request extra al servidor.

Luego usás esos datos para:

document.getElementById('username-display').textContent = payload.sub;
// muestra el nombre del usuario logueado

if (payload.role === 'admin') {
    document.getElementById('admin-controls').style.display = 'block';
    // muestra el panel de admin solo si el rol es admin
}

Función 3: loadMe().then(...) — encadenamiento de promesas

La última línea del JS es el punto de entrada que coordina todo:

loadMe().then(() => Promise.all([loadUsers(), loadItems()]));loadMe primero, después ambas en paralelo
1
loadMe() corre primero y guarda window._myUserId. Es necesario que termine antes porque loadItems() necesita ese id para hacer /users/${_myUserId}/items/count.
2
.then(...) espera a que loadMe() resuelva antes de continuar.
3
Promise.all([loadUsers(), loadItems()]) lanza ambas en paralelo — no hay dependencia entre ellas, así que no tiene sentido esperar una para empezar la otra.
Esta es la respuesta a "¿por qué no simplemente await loadMe(); await loadUsers(); await loadItems()?" — porque así las últimas dos correrían secuencialmente y tardarían el doble.

Preguntas de entrevista

¿Por qué elegiste FastAPI sobre Flask o Django?
FastAPI▼

FastAPI da validación automática con Pydantic, documentación Swagger sin configuración extra y soporte async nativo. Para una API REST es más directo que Django (que trae mucho overhead) y más moderno que Flask (sin tipado nativo). Además se integra naturalmente con SQLModel.

¿Qué hace Depends() en FastAPI?
FastAPI▼

Es el sistema de inyección de dependencias. Le decís a un endpoint que necesita algo y FastAPI lo resuelve antes de ejecutar la función. En mi proyecto lo uso para la sesión de DB (get_session) y para autenticación (get_current_user). Las dependencias se encadenan: require_admin llama internamente a get_current_user, que a su vez llama a oauth2_scheme y get_session.

¿Qué diferencia hay entre un schema y un modelo en tu proyecto?
FastAPI▼

El modelo (models.py, con table=True) es la tabla real en la DB. El schema (schemas.py) define qué datos entran y salen por la API. UserCreate recibe la password en texto plano; UserRead no la expone. Nunca devolvés el modelo directamente para evitar filtrar campos sensibles.

¿Qué pasa si mandás un tipo de dato incorrecto a un endpoint?
FastAPI▼

FastAPI devuelve automáticamente un 422 Unprocessable Entity con el detalle del error de validación antes de que llegue a tu función. No necesitás validar tipos manualmente. Por ejemplo, si mandás {"email": "no-es-email"}, Pydantic lo rechaza porque definiste email: EmailStr.

¿Para qué sirve el prefix en los routers?
FastAPI▼

Para no repetir el prefijo en cada ruta. Con APIRouter(prefix="/users"), todas las rutas del router automáticamente empiezan con /users. El tags agrupa los endpoints en la documentación Swagger.

Explicá el flujo completo de autenticación JWT en tu proyecto
JWT▼

1. POST /login con username y password.
2. authenticate_user busca el usuario en la DB y verifica la password con verify_password.
3. Si es válida, create_access_token genera un JWT firmado con la SECRET_KEY, expira en 30 min.
4. El cliente guarda el token en localStorage y lo manda en Authorization: Bearer <token>.
5. get_current_user decodifica el JWT, extrae el username (sub) y busca al usuario en la DB.

El JWT no se guarda en la DB — es stateless. No se puede invalidar sin blacklist o cambiar la SECRET_KEY.
¿Qué pasa si alguien roba el token JWT?
JWT▼

Puede usarlo hasta que expire (30 min en mi proyecto). Para mitigarlo en producción: tokens de muy corta vida + refresh tokens, HTTPS siempre, no guardar el token en localStorage si se teme XSS (usar httpOnly cookies). Esto quedó como mejora pendiente.

¿Por qué el payload del JWT no está encriptado?
JWT▼

Un JWT estándar solo firma el payload (garantiza que no fue modificado), pero no lo encripta (oculta el contenido). Cualquiera puede decodificar el Base64 y ver los datos. Por eso solo guardo username y role — nada sensible. Para encriptar el payload existe JWE, pero no es necesario para este caso de uso.

¿Qué es SQLModel y por qué lo usaste?
Base de datos▼

SQLModel combina SQLAlchemy (ORM para la DB) con Pydantic (validación). Permite definir un modelo una sola vez y usarlo como tabla de DB y como esquema de validación. Lo elegí porque se integra naturalmente con FastAPI, que ya usa Pydantic internamente.

¿Para qué sirve Alembic? ¿Por qué no usar create_all?
Base de datos▼

create_all solo crea tablas que no existen. Si necesitás agregar una columna a una tabla con datos, no hace nada. Alembic genera scripts de migración incrementales que podés aplicar y revertir, esencial en producción donde no podés borrar y recrear la DB.

¿Qué hace model_dump(exclude_unset=True) en el PATCH?
Base de datos▼

En un PATCH, solo querés actualizar los campos que el cliente mandó. exclude_unset=True devuelve solo los campos que fueron explícitamente enviados, no todos los del schema. Así si mandás solo {"full_name": "Nuevo"}, no sobreescribís el email ni el username.

¿Qué hace la lógica de negocio del endpoint POST /items/?
Base de datos▼

Si el usuario ya tiene un item con el mismo título, suma la cantidad en vez de crear uno nuevo. Es una lógica de acumulación: dos "Mouse" con cantidad 2 y 3 resultan en un solo "Mouse" con cantidad 5. Si el título es nuevo, crea el item normalmente.

¿Por qué los tests usan una DB en memoria?
Testing▼

Para que sean aislados y rápidos. Con sqlite:// (sin path de archivo) la DB vive en RAM y desaparece al terminar el test. Si usara la DB real, los tests podrían interferir entre sí o dejar datos sucios que rompan tests posteriores.

¿Qué hace app.dependency_overrides?
Testing▼

Reemplaza una dependencia de FastAPI con otra durante los tests. Reemplazo get_session (DB real) con una función que devuelve la sesión en memoria. Los endpoints se prueban en condiciones reales pero contra datos de test.

¿Qué es un fixture en pytest y para qué sirve yield?
Testing▼

Un fixture es una función que provee recursos para los tests (setup). El yield divide el fixture en dos partes: lo de antes del yield es el setup (crear la DB), lo de después es el teardown (borrar la DB). Esto garantiza que aunque el test falle, el cleanup siempre corre.

¿Qué hace el entrypoint.sh y por qué existe?
Docker▼

Corre en orden: 1) migraciones de Alembic, 2) seed de usuarios de prueba, 3) levanta uvicorn. Existe para que docker compose up deje el proyecto listo sin pasos manuales. El orden importa: las migraciones tienen que correr antes que la app.

Punto de conflicto: el seed corre en cada restart. Está protegido con if not exists, pero en producción real no debería estar en el entrypoint.
¿Por qué hay dos RUN uv sync en el Dockerfile?
Docker▼

Es una optimización de caché de capas. Docker cachea cada instrucción. Si copiás pyproject.toml e instalás las dependencias antes de copiar el código fuente, Docker reutiliza esa capa aunque el código cambie. Sin esto, cada cambio en el código reinstalaría todas las dependencias.

¿Por qué se monta database.db como volumen?
Docker▼

Sin el volumen, al hacer docker compose down los datos desaparecen porque el contenedor es efímero. El volumen persiste el archivo SQLite en el host. Limitación: SQLite con volúmenes solo puede ser accedido por un contenedor a la vez.

¿Por qué usás Promise.all en loadItems()?
JavaScript▼

Promise.all lanza ambos fetch al mismo tiempo y espera que terminen los dos. Si los hiciera secuenciales con dos await, el segundo esperaría que termine el primero sin necesidad — tardaría el doble. Los uso juntos porque no hay dependencia entre los dos requests.

¿Qué hace JSON.parse(atob(token.split('.')[1]))?
JavaScript▼

Decodifica el payload del JWT sin hacer ningún request. El JWT tiene tres partes separadas por puntos; la segunda (índice 1) es el payload en Base64. atob() decodifica el Base64 a string JSON y JSON.parse() lo convierte en objeto. Funciona porque el payload de un JWT estándar no está encriptado, solo firmado.

¿Por qué loadMe() corre antes que loadUsers() y loadItems()?
JavaScript▼

loadMe() guarda el id del usuario en window._myUserId. loadItems() necesita ese id para hacer /users/{id}/items/count. Si corrieran en paralelo, _myUserId podría no estar disponible cuando loadItems() lo necesite. Con .then() me aseguro de que loadMe termine primero.

¿Qué mejorarías si tuvieras más tiempo?
Diseño▼

Tres cosas concretas: 1) Migrar a PostgreSQL en docker-compose — más robusto que SQLite para producción. 2) Agregar autenticación al PATCH de usuarios — actualmente cualquiera puede editar a cualquier usuario, es un bug de seguridad. 3) Refresh tokens para no obligar al usuario a loguearse cada 30 minutos.

Esta respuesta muestra autocrítica real. Mucho mejor que decir "me quedó todo perfecto".
¿Por qué separaste services.py de los routers?
Diseño▼

Para separar la lógica de negocio del transporte HTTP. Los routers manejan requests y responses; los services contienen lógica que podría reutilizarse desde un CLI o un test sin pasar por HTTP. En un sistema más grande es fundamental para no mezclar responsabilidades.

¿Por qué el seed no falla si ya existen los usuarios?
Diseño▼

Antes de insertar cada usuario, consulto si ya existe con session.exec(select(User).where(User.username == u.username)).first(). Si existe, no hace nada. Esto permite que el seed corra múltiples veces (como en cada restart de Docker) sin duplicar datos ni tirar errores.

¿Qué es una cooperativa de trabajo y cómo te ves trabajando ahí?
Diseño▼

En una cooperativa los miembros son parte de la organización — hay más horizontalidad y decisiones colectivas. Mencionar que valorás el trabajo colaborativo, la transparencia y que podés adaptar tu forma de trabajar a un contexto donde las decisiones no son top-down. Es bueno mostrar interés genuino en el modelo cooperativo, no solo en el trabajo técnico.
