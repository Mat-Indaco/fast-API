SECRET_KEY con fallback inseguro y .env en el repo SEGURIDAD
▶

El problema es doble. Primero, el fallback "changeme-insecure-default": si la variable de entorno no se carga, la app arranca igual con una clave que cualquiera que vio mi repo conoce. Con esa clave un atacante puede firmar sus propios JWT con "sub": "admin" y entrar como administrador sin contraseña. La firma HS256 solo es segura si la clave es secreta.

Segundo, mi .env con el SECRET_KEY real está commiteado en el repo, así que el secreto ya está expuesto de hecho.

Cómo lo corregiría: que la app falle al arrancar si no existe la clave (os.environ["SECRET_KEY"] sin default, o validándolo con pydantic-settings), nunca un fallback. Sacar .env del repo, agregarlo a .gitignore, dejar solo un .env.example sin valores reales, y rotar la clave porque ya quedó comprometida. En producción la clave va en un gestor de secretos, no en un archivo.

5
Flujo completo del login
▶

El cliente hace POST /login con username y password como form-data. FastAPI los parsea con OAuth2PasswordRequestForm (por eso es form y no JSON: es el estándar OAuth2). Llamo a authenticate_user, que busca el usuario por username y, si existe, compara la contraseña con verify_password, que internamente usa argon2 para hashear la contraseña recibida y compararla con el hash guardado. Nunca comparo texto plano.

Si las credenciales son válidas, genero el token con create_access_token, que arma un payload con sub (el username), role, y un exp (ahora + 30 min), y lo firma con la SECRET_KEY y HS256. Devuelvo {access_token, token_type: "bearer"}.

A partir de ahí, en cada request a un endpoint protegido el cliente manda Authorization: Bearer <token>. OAuth2PasswordBearer extrae el token, y get_current_user lo decodifica con jwt.decode (verifica firma y expiración), saca el sub, busca ese usuario en la DB y lo devuelve. Si el token es inválido, expiró, o el usuario no existe, tiro 401. Los endpoints que dependen de get_current_user reciben el usuario ya autenticado por inyección de dependencias.

6
role en el token pero require_admin re-consulta la DB
▶

Es una decisión sobre confiar en el token vs. confiar en la base. Meto el role en el JWT, pero a la hora de autorizar (require_admin) leo el rol desde el usuario que get_current_user trajo de la DB, no desde el token.

Ventaja de re-consultar: el dato siempre está fresco. Si a un usuario le saco el rol de admin, pierde permisos en su próxima request aunque su token viejo todavía diga "role": "admin". El token es inmutable hasta que expira; la DB es la fuente de verdad. Desventaja: una query extra a la DB en cada request protegida.

Si confiara solo en el token me ahorro la query (más rápido, escala mejor, es la gracia de un JWT stateless), pero quedo con el problema de revocación: un cambio de rol no tiene efecto hasta que el token expira. En este proyecto, como ya consulto la DB para traer el usuario, aprovecho y leo el rol de ahí; el role del token es redundante. En un sistema de alto tráfico evaluaría confiar en el claim del token y aceptar tokens de vida corta + refresh para mitigar la revocación.

7
Por qué argon2 y qué es un salt
▶

Uso argon2 (vía pwdlib) porque es un algoritmo de hashing diseñado específicamente para contraseñas: ganó la Password Hashing Competition y es el recomendado hoy. La clave es que es deliberadamente lento y consume memoria, lo que hace carísimo un ataque de fuerza bruta.

SHA-256 es lo contrario: es rápido y pensado para integridad, no para contraseñas — un atacante puede probar miles de millones de hashes por segundo, así que nunca se usa para passwords. bcrypt sería una alternativa válida y aceptada, pero argon2 es más moderno y resistente a ataques con GPU/ASIC por su uso de memoria.

Un salt es un valor aleatorio único que se agrega a cada contraseña antes de hashearla. Sirve para que dos usuarios con la misma contraseña tengan hashes distintos, y para que no se puedan usar rainbow tables (tablas precomputadas de hash→password). argon2 genera y guarda el salt automáticamente dentro del propio string del hash, por eso no lo manejo a mano.

8
Refresh tokens
▶

Hoy mi access token dura 30 minutos y no hay refresh: cuando expira, el usuario tiene que volver a loguearse. El patrón estándar es tener dos tokens. Un access token de vida corta (15–30 min) que viaja en cada request, y un refresh token de vida larga (días o semanas) que solo se usa contra un endpoint /refresh para obtener un access token nuevo sin reingresar credenciales.

Dónde guardarlos: el refresh token idealmente en una cookie httpOnly, Secure y SameSite, para que el JavaScript del navegador no pueda leerlo y mitigar XSS. El access token puede ir en memoria del cliente.

Además, para poder revocar, guardaría los refresh tokens en la DB (o Redis) con su estado, de modo que un logout o un robo de token se pueda invalidar del lado servidor — esto resuelve justo el problema de revocación de la pregunta 6. Una práctica adicional es la rotación: cada vez que se usa un refresh token, se invalida y se emite uno nuevo, así detectás reutilización.

10
Condición de carrera en create_item
▶

En create_item, cuando el item ya existe, hago: leo el item, le sumo cant, y guardo. Eso es un patrón read-modify-write que no es atómico. Si llegan dos requests concurrentes del mismo usuario con el mismo título, ambas pueden leer cant=5 al mismo tiempo, una suma 3 y guarda 8, la otra también leyó 5, suma 2 y guarda 7 — se pierde una actualización (lost update). El total queda mal.

Cómo lo resolvería: la forma más limpia es hacer la suma en la base de datos de forma atómica, con un UPDATE items SET cant = cant + :n WHERE ... en vez de leer-en-Python-y-escribir; la DB serializa esa operación. Otra opción es un lock pesimista (SELECT ... FOR UPDATE) para bloquear la fila, o un control optimista con una columna de versión que detecte el conflicto y reintente.

Y para garantizar la unicidad real conviene un constraint UNIQUE(owner_id, title) en la tabla, así la integridad no depende solo de mi chequeo en código.

Nota: con SQLite esto casi no se nota por su locking de archivo, pero en PostgreSQL con concurrencia real es un bug que aparece.

Optimizar /users/ cuando va lento
▶

Primero mido, no adivino. Miro el tiempo de la request y el EXPLAIN ANALYZE de la query para ver si hace un sequential scan, y reviso logs de queries lentas. Las causas típicas y sus soluciones:

Índices: si filtro u ordeno por una columna sin índice, agrego uno (en mi modelo ya tengo username e Item.title indexados).

Paginación: ya la tengo con offset/limit, pero un OFFSET grande es lento porque la DB igual recorre las filas saltadas; en tablas grandes pasaría a keyset pagination (paginar por id > último_visto).

N+1: el problema clásico — si por cada usuario hiciera una query para traer sus items, son cientos de queries; se resuelve con un join o selectinload para traer todo en una o dos queries.

Payload: devolver solo las columnas necesarias con un response_model acotado. Y si el dato se consulta mucho y cambia poco, una capa de caché con Redis. La regla es: medir, encontrar el cuello de botella real, y recién ahí optimizar.

19
Express / NestJS vs FastAPI
▶

Las tres son buenas para APIs REST; la elección depende del contexto. FastAPI me da validación y serialización automática con Pydantic basada en type hints, documentación OpenAPI/Swagger gratis, y soporte async nativo, con muy poco código. NestJS es muy parecido en filosofía a FastAPI pero en TypeScript: arquitectura opinada con módulos, inyección de dependencias y decoradores, ideal para equipos grandes y proyectos que necesitan estructura. Express es minimalista y sin opiniones: máxima libertad pero tenés que armar vos validación, estructura y middlewares.

Cuándo elijo cada uno: FastAPI/Python si el proyecto tiene componente de datos, ML o cálculo científico, o si el equipo es Python. Node (Nest o Express) si el equipo ya es full JS/TS y quiero compartir tipos y lógica entre front y back, o por el ecosistema npm. Nest sobre Express cuando el proyecto va a crecer y quiero convenciones desde el día uno; Express para algo chico o un microservicio simple.

En rendimiento crudo de I/O son comparables; la diferencia real suele estar en el lenguaje del equipo y la mantenibilidad.

Despliegue a producción
▶

Arrancaría desde lo que ya tengo (Dockerfile + compose + CI) y le sumaría lo que falta para producción.

Configuración y secretos: nada de .env en el repo; las variables (SECRET_KEY, credenciales de DB) van inyectadas por el entorno o un gestor de secretos.

Base de datos: migrar de SQLite a PostgreSQL gestionado, y correr las migraciones de Alembic en el deploy (ya lo hago en el entrypoint.sh).

Servidor: en vez de un solo uvicorn, uvicorn con varios workers gestionados por gunicorn para aprovechar todos los cores.

Red y seguridad: un reverse proxy (Nginx o el del cloud) que termine HTTPS/TLS, CORS configurado para permitir solo mi front, y headers de seguridad.

Observabilidad: ya tengo sentry-sdk para errores; sumaría logging estructurado y un /health para que el orquestador sepa si la app está viva.

CI/CD: mi pipeline ya corre lint y tests; lo extendería para que, si pasa, construya la imagen Docker y la despliegue automáticamente. Y antes de exponerlo, cerrar los agujeros ya identificados: el registro de admins, los endpoints sin auth y el secret comprometido.
